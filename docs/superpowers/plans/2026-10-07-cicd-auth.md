# CI/CD-ready auth: `.env` scaffolding, `mm diff --check`, client-credentials auth

## Context

Users should be able to run the CLI with scoped app access tokens and wire deployment into CI/CD. Token auth + `.env` loading already work (`packages/cli/src/load-env.ts`), but three gaps remain:

1. `mm init` tells the user to create `.env` by hand and nothing prevents committing it.
2. `diff` exits 0 even with drift (`docs/CLI.md` §8 explicitly notes "no --check mode"), so CI can't gate on "store in sync".
3. Shopify has **removed admin-created custom apps** — new stores can't mint a permanent `shpat_` token in the admin UI. The Dev Dashboard replacement is the **client credentials grant**: persist client ID + secret, exchange for a 24h token via `POST https://{shop}/admin/oauth/access_token` (`grant_type=client_credentials`, form-encoded → `{ access_token, scope, expires_in: 86399 }`). The CLI must mint the token itself; nothing persistable exists for these users. (Verified against shopify.dev docs, 2026-10.)

All three were designed and approved in conversation. TDD throughout (red → green per behavior).

## Task 1 — `mm init` writes `.env` and guards `.gitignore`

File: `packages/cli/src/init.ts` (+ `init.test.ts`)

- `runInit` gains `opts.env?: NodeJS.ProcessEnv` (default `process.env`) for testability, mirroring the injected `run` in `auth.ts`.
- **`.env`** — written only if absent (same never-overwrite rule as the other scaffolds; never append/merge an existing one):
  - `SHOPIFY_ADMIN_TOKEN` set in the environment → write `SHOPIFY_ADMIN_TOKEN=<value>` (persisting the already-exported token; never echo the value to the console).
  - Otherwise → placeholder: comment pointing at the two auth routes + empty `SHOPIFY_ADMIN_TOKEN=` line + commented `# SHOPIFY_CLIENT_ID=` / `# SHOPIFY_CLIENT_SECRET=` lines (for task 3).
- **`.gitignore`** — the one file init may *modify*: create with `.env` if missing; append `.env` if present and no line equals `.env` or `/.env`; untouched if already covered.
- Console "Next:" message reflects what happened (token persisted vs. paste needed).

Tests: placeholder when env var absent; real value when present; existing `.env` untouched; `.gitignore` created / appended / left alone.

## Task 2 — `mm diff --check`

Files: `packages/cli/src/index.ts`, `args.test.ts` (and/or `commands.test.ts`)

- `parseArgs`: new boolean `check` flag (parsed globally like `--force`; only `diff` reads it).
- `runDiff` already returns `{ definitions, metafields, entries }` (`packages/cli/src/diff.ts:12`) — no change there. In `main`'s diff branch, with `--check`, return **exit 2** when any op list is non-empty, via a small exported pure helper (e.g. `checkExitCode(result): 0 | 2`) so it's testable without faking `main`.
- Exit-code contract stays one-dimensional: `0` clean, `1` config/transport error, `2` store ≠ desired state (now for both `push` and `diff --check`).
- Update `HELP` text in `index.ts`.

Tests: `--check` parses (incl. `--check=x` rejected); `checkExitCode` → 2 on drift in each of the three lists, 0 when all empty.

## Task 3 — `auth: "client-credentials"`

Core (`packages/core`):
- `src/config.ts`: `AuthMode` gains `"client-credentials"`; new `ClientCredentialsConfig extends BaseConfig { auth: "client-credentials"; clientId: string; clientSecret: string; accessToken?: string }` added to the `Config` union; `validateConfig` requires `shop`/`schema`/`clientId`/`clientSecret` for this mode and updates the auth-mode error message.
- `src/node/` (new `client-credentials.ts`, re-exported from `src/node/index.ts` — stays inside the `./node` export, zero new deps): `createClientCredentialsAdminClient({ shop, clientId, clientSecret, apiVersion })`. Mints the token on first GraphQL call via `fetch` to `https://{shop}/admin/oauth/access_token` (form-encoded body), caches it for the process lifetime (CLI runs last seconds; no refresh/401-retry logic), then behaves exactly like `createAdminClient` (`src/node/client.ts:13`) including `SyncTransportError` wrapping. Token-mint failure (e.g. `shop_not_permitted`) → `SyncTransportError` with the response body as cause.
- Export anything the CLI needs from core's `src/index.ts` / node entry (tsup bundles; no deep imports).

CLI (`packages/cli`):
- `src/auth.ts` `selectAdminClient`: new branch for `"client-credentials"`. **No** `$app`-scope guard — the token belongs to the user's own app, so `$app` resolves correctly (doc note: this is an advantage over `auth: "cli"`). `cliAuthAppScopeNotice` already no-ops for non-`"cli"` auth.
- `src/init.ts` config template: commented `// auth: "client-credentials", clientId/clientSecret` block, same pattern as the existing `// auth: "cli"` hint.

Tests: config validation (missing clientId/secret, bad auth value); client test with a faked `fetch` — token endpoint request shape (URL, form body), `X-Shopify-Access-Token` header on the subsequent GraphQL call, single mint across multiple calls, transport-error path. Follow existing patterns in core's node client tests / CLI `auth.test.ts`.
