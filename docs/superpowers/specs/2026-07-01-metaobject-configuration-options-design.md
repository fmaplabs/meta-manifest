# meta-manifest — additional metaobject configuration options (design)

**Date:** 2026-07-01
**Status:** Proposed (awaiting review)
**Scope of this spec:** new declarative configuration options for metaobject definitions (scope, merchant-editability,
capabilities, access, display name, field filters) exposed through the builder + config, mapped to the Admin API, and
made reconcilable through the existing `pull` → `diff` → `push` sync pipeline. No dashboard/UI work.

## 1. Context & goals

`@fmaplabs/meta-manifest` declares Shopify **metaobject definitions** in code and syncs them to a store. Today the
builder exposes a partial slice of the definition surface: `name`, `description`, `displayName`, `access.admin`,
`access.storefront`, `capabilities.publishable`/`translatable`/`renderable` (booleans), and field
`key`/`type`/`required`/`validations`. This spec adds the remaining developer-facing configuration a Shopify app needs:

1. Declare whether **all** metaobjects are **app-scoped** or **merchant-scoped**.
2. Declare metaobjects **editable by merchants**.
3. Per metaobject: **active/draft status**, **translations**, **publish entries as web pages**, **Storefront API
   access**, **Customer Account API access**, **display name** (auto-generated by default), and **fields used as
   filters**.

A large part of (3) already exists partially in `define.ts` and is *fetched but discarded* by the sync layer; the work
is as much "complete + expose + reconcile + document + test" as it is greenfield. The genuinely new API pieces are
`access.customerAccount`, `capabilities.onlineStore` (web pages), per-field `adminFilterable` (filters), and the
app/merchant scope + merchant-editable toggles.

## 2. Decisions (locked)

| #   | Decision | Choice |
| --- | --- | --- |
| 1 | Scope placement | **Global `scope` in `defineConfig` (default `"app"`) + optional per-metaobject `scope` override.** Effective type resolved at **sync time** (normalize), so `Author.type` stays the eager canonical `$app:<handle>`. |
| 2 | Drift reconciliation | **Full reconciliation.** Access, capabilities, display name, description, and field filters are diffed and updated on existing definitions (not create-only). |
| 3 | Merchant-editable | Global `merchantEditable` convenience in config (default `false`) sets the default admin access; explicit per-metaobject `access.admin` overrides. Both kept. |
| 4 | Web pages | Map to `capabilities.onlineStore` as an **object** (`{ urlHandle, createRedirects? }`) because Shopify requires a non-null `urlHandle`; presence enables, absence disables. |
| 5 | Renderable (SEO) | Extend existing `renderable: boolean` to `true \| { metaTitleKey?, metaDescriptionKey? }` (backward compatible). |
| 6 | Filters | Per-**field** builder option `filterable?: boolean` → field `capabilities.adminFilterable`. |
| 7 | Capability naming | Mirror Shopify names 1:1 (`publishable`/`translatable`/`renderable`/`onlineStore`); no invented aliases. |
| 8 | Destructive gating | Scope change on an existing definition (type-identity change → drop/recreate) and `onlineStore` disable are gated behind the existing destructive path (`--force` / `allowDestructive`). Everything else reconciles directly. |

## 3. Verified Shopify ground truth

Confirmed against shopify.dev Admin API docs (2026-07), not memory. Record so the plan does not re-derive.

- **`MetaobjectAccessInput`** fields: `admin`, `storefront`, **`customerAccount`**.
  - `admin` (`MetaobjectAdminAccessInput`): settable values are **only** `MERCHANT_READ`, `MERCHANT_READ_WRITE`.
    Settable **only on app-reserved (`$app:`) types** — otherwise userError `ADMIN_ACCESS_INPUT_NOT_ALLOWED`.
  - `storefront` (`MetaobjectStorefrontAccess`): `NONE`, `PUBLIC_READ`.
  - `customerAccount` (`MetaobjectCustomerAccountAccess`): `NONE`, `READ` (**no write**).
- **`MetaobjectCapabilityCreateInput`** fields (each `{ enabled: Boolean! }` plus optional `data`):
  - `publishable` → ACTIVE/DRAFT status.
  - `translatable` → translations via translation APIs.
  - `renderable` → SEO metadata; `data: { metaTitleKey, metaDescriptionKey }` (field-key aliases).
  - `onlineStore` → renders entries as Online Store web pages; `data: { urlHandle: String!, createRedirects: Boolean = false }`.
    Independent of `renderable`; the docs' "web pages" example enables both, but neither requires the other.
    **Not supported in `shopify.app.toml`** — only via GraphQL (a differentiator for this GraphQL-driven tool).
- **Per-field `MetaobjectFieldDefinitionCreateInput.capabilities.adminFilterable`** (`{ enabled: Boolean! }`) → "use as
  filter" in the admin. This is the mapping for "fields used as filters."
- **`displayNameKey`** is optional on the definition input; omitting it lets Shopify **auto-generate** the display name.
- **Type/scope:** app-scoped type is `"$app:<handle>"` (Shopify resolves/returns `"app--<appId>--<handle>"`);
  merchant-scoped is a bare `"<handle>"`. `type` is **immutable** after creation.
- **Update path:** `metaobjectDefinitionUpdate(id, definition: MetaobjectDefinitionUpdateInput)` accepts `name`,
  `description`, `displayNameKey`, `access`, `capabilities`, and `fieldDefinitions` — so definition-level metadata *can*
  be updated (today's `push` only sends `fieldDefinitions`).

## 4. Current-state facts that shape the work

- `defineMetaobject` hardcodes `type = \`$app:${handle}\`` (`define.ts:61`); `Author.type` is eager and consumed by
  `m.ref()`, `encode`/`parse`, codegen, and diff identity.
- `m.ref` stores its target as a **validation** `{ name: "metaobject_definition_type", value: "$app:author" }`
  (`fields/reference.ts:57-59`); `shopifyType` stays `"metaobject_reference"`. Lists use the plural
  `metaobject_definition_types` (JSON array). `referenceEdges` (`push.ts:45`) reads both.
- **The pull query already fetches** `access { admin storefront }`, `capabilities { publishable translatable
  renderable }`, `displayNameKey`, `description`, and per-field `name`/`description`/`validations`
  (`client.ts:15-37`) — but `normalize.ts` keeps only `type`/`name`/`fields{key,type,required,validations}` and
  **discards the rest** before `diff`. The `LIST` query (codegen path) does *not* fetch metadata yet.
- `diff` compares by `type` equality and emits only `createDefinition` + field ops; there is **no** definition-metadata
  op. `push` update sends `{ fieldDefinitions }` only (`push.ts:185`).
- Remote `app--<id>--<handle>` is re-labeled to canonical `$app:<handle>` in `pull` (`pull.ts:54-58`);
  `pullAll` keeps bare/merchant types when `appOwnedOnly: false`.

## 5. Public API / syntax

### 5.1 Config (global defaults — requirements 1 & 2)

```ts
// meta-manifest.config.ts
export default defineConfig({
  shop: "my-store.myshopify.com",
  accessToken: process.env.SHOPIFY_ADMIN_TOKEN!,
  schema: "./schema.ts",
  scope: "app",             // "app" (default) | "merchant" — applies to ALL metaobjects
  merchantEditable: false,  // default admin access: false → merchant_read, true → merchant_read_write (app scope only)
});
```

### 5.2 Per-metaobject (requirement 3 + overrides)

```ts
export const Author = defineMetaobject("author", {
  name: "Author",
  displayName: "name",              // optional; omit → Shopify auto-generates
  scope: "merchant",                // optional override of config.scope
  access: {
    admin: "merchant_read_write",   // optional explicit override (app scope only)
    storefront: "public_read",      // existing — "public_read" | "none"
    customerAccount: "read",        // NEW — "none" | "read"
  },
  capabilities: {
    publishable: true,                                              // active/draft (existing)
    translatable: true,                                             // translations (existing)
    renderable: { metaTitleKey: "name", metaDescriptionKey: "bio" }, // SEO; also accepts `true`
    onlineStore: { urlHandle: "authors", createRedirects: true },   // NEW — publish as web pages
  },
  fields: {
    name: m.text({ required: true, filterable: true }),  // NEW — filterable → adminFilterable
    bio: m.multilineText(),
  },
});
```

### 5.3 Type changes

```ts
// config.ts
export interface Config {
  shop: string; accessToken: string; apiVersion?: string; schema: string;
  scope?: "app" | "merchant";          // default "app"
  merchantEditable?: boolean;          // default false
}

// define.ts
export interface AccessConfig {
  admin?: "merchant_read" | "merchant_read_write";
  storefront?: "public_read" | "none";
  customerAccount?: "none" | "read";                          // NEW
}
export type RenderableConfig = boolean | { metaTitleKey?: string; metaDescriptionKey?: string };
export interface OnlineStoreConfig { urlHandle: string; createRedirects?: boolean }   // NEW
export interface CapabilitiesConfig {
  publishable?: boolean;
  translatable?: boolean;
  renderable?: RenderableConfig;                              // widened
  onlineStore?: OnlineStoreConfig;                            // NEW
}
export interface MetaobjectConfig<F> {
  name: string;
  description?: string;
  displayName?: keyof F & string;
  scope?: "app" | "merchant";                                // NEW (override)
  access?: AccessConfig;
  capabilities?: CapabilitiesConfig;
  fields: F;
}

// fields/base.ts — shared field option
interface BaseFieldOptions { /* ...existing... */ filterable?: boolean }   // NEW → adminFilterable
```

`filterable` lives on the shared base field options so every field type accepts it (idiomatic for the zod-style
builder), and is read by `definition-input`/`normalize` the same way `name`/`description` are.

## 6. Scope resolution (sync-time rewrite)

`Author.type` stays eager `$app:<handle>`. The sync pipeline gains a resolution step, given `config.scope` +
`merchantEditable` and the full schema set:

1. Compute each metaobject's **effective scope**: per-metaobject `scope` → else `config.scope` → else `"app"`.
2. Build a map `handle → effectiveType` (`$app:<handle>` for app, bare `<handle>` for merchant).
3. In `normalizeLocal` (and before `pull`), for a merchant-scoped definition rewrite the **`type`**
   `$app:<handle>` → `<handle>`.
4. Rewrite **reference targets**: any `metaobject_definition_type` value, and each element of a
   `metaobject_definition_types` JSON array, is remapped to the *referenced* metaobject's effective type (keyed by that
   target's own scope, so mixed app/merchant graphs resolve correctly). `metaobject_reference` `shopifyType` is
   unchanged.

The effective type is used consistently for the pull query, diff identity, `create`, and dependency edges. `Author.type`
and `m.ref` public values remain the canonical `$app:` form (README guarantee `Author.type === "$app:author"` holds).

## 7. Definition input mapping (`definition-input.ts`)

`toDefinitionInput` gains, driven by the (already-resolved) config:

- `access.customerAccount` → `access.customerAccount` (uppercased enum).
- `capabilities.renderable` object → `{ enabled: true, data: { metaTitleKey?, metaDescriptionKey? } }`; `true` →
  `{ enabled: true }`; absent/`false` → omitted or `{ enabled: false }` (see §8 for the enabled/disabled contract).
- `capabilities.onlineStore` → `{ enabled: true, data: { urlHandle, createRedirects? } }`.
- `merchantEditable` / `access.admin` resolution → `access.admin` (only for app scope; omitted for merchant scope).
- Per field: `filterable` → `capabilities: { adminFilterable: { enabled: true } }` on `FieldDefinitionInput`.

`FieldDefinitionInput` and `MetaobjectDefinitionInput` grow the corresponding optional fields.

## 8. Full drift reconciliation

- **Thread metadata through `normalize`.** `RemoteDefinition` grows `access`, `capabilities` (normalized to a
  comparable shape), `displayNameKey`, `description`; `RemoteField` grows `filterable`. `normalizeRemote` reads the
  already-fetched data; `normalizeLocal` emits it from the resolved definition input.
- **New diff op `updateDefinition`.** Emitted when any of `name`/`description`/`displayNameKey`/`access`/`capabilities`
  differ; carries the new values. `updateField` additionally detects `filterable` drift.
- **Push applies it** via `metaobjectDefinitionUpdate` with `{ name?, description?, displayNameKey?, access?,
  capabilities? }` (extending the current fields-only update). Field capabilities ride along in field create/update
  payloads.
- **Enabled/disabled contract.** To reconcile a capability being turned off, normalized capabilities represent both
  enabled and disabled states (`{ enabled: boolean }`) rather than presence/absence, so `diff` can tell "was on, now
  off" from "unchanged."
- **GraphQL extensions (`client.ts`).** Add to the pull query: `access { customerAccount }`,
  `capabilities { renderable { data { metaTitleKey metaDescriptionKey } } onlineStore { enabled data { urlHandle
  } } }`, and per-field `capabilities { adminFilterable { enabled } }`. Extend the `LIST` query with the same metadata
  so `pullAll`/codegen round-trip it.
- **Destructive gating (decision 8).** A scope change flips the `type` identity → surfaces as remove + create
  (destructive, `--force`). Disabling `onlineStore` removes live pages → gated. Other capability/access changes
  reconcile directly.

## 9. Codegen (`codegen.ts`)

`pull` emits the new options when present: `scope` (when the pulled type is bare/merchant), `access.customerAccount`,
`capabilities.renderable` data, `capabilities.onlineStore`, and per-field `filterable`. Requires the `LIST` query
metadata from §8.

## 10. Validation & edge cases

- `scope: "merchant"` **and** an explicit per-metaobject `access.admin` → author-time validation error (admin access is
  invalid on merchant-owned types; the merchant already has full access). The global `merchantEditable` default simply
  does not apply to merchant-scoped definitions (admin access is omitted for them) and is not an error.
- `onlineStore` without `urlHandle` → TypeScript type error (required field).
- `renderable`/`onlineStore` referencing a `metaTitleKey`/`metaDescriptionKey` that is not a declared field key →
  validation error before push.
- `customerAccount: "read"` is only meaningful alongside a Storefront/Customer surface, but is independently valid; no
  cross-check.
- Existing schemas with `renderable: true` keep working (widened union is backward compatible).

## 11. Testing

- **Unit — `definition-input`:** each new option maps to the correct input shape (customerAccount enum, renderable
  data, onlineStore data, adminFilterable, merchantEditable→admin resolution).
- **Unit — scope:** effective-scope resolution (override > config > default); type rewrite; reference rewrite for
  single + list refs; mixed app/merchant graph.
- **Unit — diff:** `updateDefinition` emitted on access/capability/displayName/description drift; `filterable` drift in
  `updateField`; scope change surfaces as destructive.
- **Unit — push:** update payload includes access/capabilities/displayName; destructive gating for scope-change and
  onlineStore-disable.
- **Unit — validation:** merchant+admin conflict, unknown SEO field keys.
- **e2e:** extend the existing sync e2e (if the live-store path is exercised) to cover create + update of the new
  options.
